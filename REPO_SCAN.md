## 1. What this repository is

Two independent halves that share a job dataset, plus two static dashboards:

| Half | Entry point | Purpose |
| --- | --- | --- |
| Python bot | `main.py` (Flask + pyTelegramBotAPI) | Searches the web, verifies vacancies, applies (Playwright), publishes to Telegram, serves the admin dashboard. |
| Node scraper | `tn-live-jobs/src/cli.js` | Scrape → validate → diff → export → report pipeline; publishes a static job board under `tn-live-jobs/public/`. |
| Static dashboards | `docs/` and root `index.html` / `server.js` | `docs/` is deployed by `.github/workflows/static.yml`; root `index.html` is a 651 KB single-file board served by the Express app in `server.js`. |

Tracked files: **124**. Single commit history (`e368f50 feat: enhance dashboard UI and resume generation`).

## 4. Findings

### Critical

**C1 - `cloud_runner.py` is missing, and CI runs it.**
`.github/workflows/job_bot.yml:120` executes `python cloud_runner.py`, but the
file does not exist in the working tree and was never committed (no history).
Every scheduled/manual run of the `Telegram Job Bot Cloud Automation` workflow
therefore fails at the "Run Telegram Job Bot Cloud Cycle" step, after doing the
scrape work. The file is also imported by `test_cloud_runner.py` (6 errors) and
read directly by `test_job_discovery.py:131`, so the offline suite cannot pass
either. This is the highest-impact defect: the repository as committed cannot
complete its own CI.

### High

**H1 - `tn-live-jobs/package-lock.json` is missing but `npm ci` is used.**
`.github/workflows/job_bot.yml:85` caches on `tn-live-jobs/package-lock.json`
and line 90 runs `npm ci`, which hard-fails without a lockfile. Reproduced:
`npm ci` -> "Run `npm help ci` for more info". `tn-live-jobs/README.md:116`
explicitly claims the lockfile "is committed, so installs are exact" - it is
not. The workflow's Node install step fails before any Node test runs.

**H2 - `.github/workflows/verify.yml` is missing.**
`AGENTS.md:79` and `test_workflows.py` both assume a PR verification workflow
(`verify.yml`) that runs the Python offline suite, Playwright browser tests and
the two Node test files. It does not exist. `test_workflows.py` fails with
`FileNotFoundError` (`test_workflow_files_exist`,
`test_verification_workflow_has_no_secret_references`).

**H3 - `engineering_app.py` is missing.**
`ENGINEERING_SEARCH.md` and `OPTIMIZATION.md` describe `engineering_app.py` as
the opt-in launcher and include it in `py_compile` instructions. It is not in
the tree. The engineering feature is documented as runnable but its entry point
does not exist (only `engineering_telegram.py` is present).

### Medium

**M1 - No `.gitignore` exists, contradicting the workflow and README.**
`job_bot.yml` comments and `README.md:46` state that dedup/state files
(`applied_jobs.json`, `radar_seen_jobs.txt`, `job_discovery_state.json`, ...)
are `.gitignore`d and must be force-added with `git add -f`. There is no
`.gitignore` in the tree, so those files are ordinary tracked files. The `-f`
in the workflow is harmless today but the documented invariant is false, and
runtime-only state (e.g. `job_discovery_state.json`) is not actually protected
from an accidental `git add .`.

**M2 - `__pycache__/` is committed (14 `.pyc` files, `cpython-310`).**
Build artifacts are tracked. They are Python 3.10 bytecode while CI runs 3.11,
so they are stale and never loadable; they add noise and can mask a
missing-source problem. They should be removed and ignored.

**M3 - Documentation drift.**
- `tn-live-jobs/README.md:67,122` references `.github/workflows/tn-jobs.yml`,
  which does not exist. The Node pipeline is actually invoked from the root
  `.github/workflows/job_bot.yml` (`npm run scrape`).
- `tn-live-jobs/README.md` describes a 6-hourly `cron` and a `publish` Pages
  job that are not present in the repository.
- `README.md` lists `test_cloud_runner.py` in the offline suite, but its
  module is absent (C1).
- `AGENTS.md` documents `verify.yml` and `npm run engineering:test`; the former
  is absent, the latter exists.

**M4 - No license.**
`README.md:107` notes the repository needs an owner-selected root license.
`tn-live-jobs/package.json` declares `"license": "MIT"` for the subproject only.
There is no `LICENSE`/`COPYING` file.

### Privacy / hygiene

**P1 - Personal data committed.** `profile.json` contains a real name, personal
email (`manojprofessional007@gmail.com`) and phone number, and the same email
appears in `email_receipts.json` / `applied_jobs_log.csv`. `README.md:103`
acknowledges this was "intentionally preserved" but it is live PII in a public
repo and should be scrubbed or moved to private config.

**P2 - Firebase web config committed.** `firebase-applet-config.json` includes
the Firebase `apiKey` and project identifiers. Web Firebase keys are not
secrets, but they are project-identifying and should be paired with strict
Firestore rules (`firestore.rules` is present).

**P3 - `resume.pdf` / `test_resume.pdf` committed**, and `applied_jobs_log.csv`
contains many scraped Telegram-channel links (some pointing at
`policies.google.com/privacy`, `telegram.me/...` promo posts), which suggests
the applier sometimes records non-jobs as "Applied".

## 5. Architecture notes worth keeping

- **Publication gate:** only `verified: true` jobs reach
  `tn-live-jobs/public/data/`; unverified records stay in `data/jobs.json`.
- **Export safety guard** refuses to overwrite good data when every source
  fails (`tn-live-jobs/src/export.js`).
- **Politeness:** `scraper.js` serialises per-domain requests (`runExclusive`)
  with 1.5-3.5 s spacing; `SOURCE_CONCURRENCY` (default 3) only parallelises
  across different domains. `runWithConcurrency` (`concurrency.js`) is the
  shared bounded-parallel helper and preserves input order.
- **City list is duplicated** between `tn-live-jobs/src/config.js` (`CITIES`)
  and `job_radar.py`; `test_priority_cities.js` asserts parity and passed.
- **Bot search paging** returns `{results, page, has_more, total_available}`
  and the `search_more:<md5>:<page>` callback keeps `callback_data` <= 64 bytes
  (asserted by `test_job_discovery.SearchQualityTests`).
- **SEO files are generated** by `export.js` `writeSeoFiles()`; edit the
  generator, not the committed `sitemap.xml` / `robots.txt`.
